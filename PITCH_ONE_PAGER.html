REST vs GraphQL repo analysis & key points · rest-vs-graphql · Spring Boot 4.0.6 · Java 25 · WebFlux + Spring GraphQL · R2DBC MySQL

One service serves both the API and the demo page. The pitch is not “GraphQL beats REST” — it is: what changes when clients choose their own response shape?

01 · What it is

ShapeREST GET + GraphQL POST against one MySQL bookstore
BackendWebFlux (reactive Netty), Spring for GraphQL 2.0.3
DataR2DBC MySQL via reactive DatabaseClient
Seed200 authors · 10,000 books · 25,054 reviews

Seeding is idempotent: each boot verifies counts and rebuilds only when data is missing or stale. Three consecutive boots logged the same 25,054 reviews, proving the data is not regenerated on boot.

02 · Endpoints

GET  /api/rest-vs-graphql/catalog/full|light?limit=N
GET  /api/rest-vs-graphql/book/{id}
GET  /api/rest-vs-graphql/status
POST /graphql
  books(limit:Int=10) { books meta{dbCalls rowsLoaded elapsedMs} }

Catalog and book replies carry Cache-Control: max-age=60, public; status is no-store. REST uses a {status,data} envelope.

03 · What the demo proves

  • Over-fetching is visible: full REST sends 11 fields, the card uses 5 → 6 extra (55%).
  • REST can be lean too: light REST sends exactly the 5 fields the card needs, which blocks the lazy “REST is inherently wasteful” takeaway.
  • Field evolution: toggling description is a GraphQL query edit, but a backend contract change for light REST.
  • Caching asymmetry: GET inherits browser/CDN caching for free; GraphQL POST does not by default.

05 · Recommendation

Keep REST for stable, cacheable public APIs. Use GraphQL behind a BFF where client flexibility and cross-resource composition justify the guardrails. Batch before launch; add depth and complexity limits, persisted queries and per-query metrics before exposing it.

06 · Server cost — the punchline

GraphQL selectionSQL calls
scalar fields only1
+ author1 + N
+ reviews1 + N
+ author + reviews1 + N + N

Measured at limit=10 with both nested: 21 SQL calls, 48 rows, 27–72 ms. At limit=100 the same shape predicts 201 calls.

This N+1 model is deliberate for teaching, and it is also the honest operational risk: production GraphQL needs batching, depth and complexity limits, and persisted queries.

09 · What we’ve done

  • Extracted the feature into its own repo; trimmed the pom, config and README and translated the last Chinese strings — the repo is all English now.
  • Hardened the launcher: NAME=VALUE arguments are honoured (they were silently ignored, which caused the empty-password failure), bare words are rejected, and -h was added. Verified under bash and zsh.
  • Added dev-only request and SQL logging so the UI cost numbers can be audited in the console.
  • Verified end to end: 12 backend tests, 19 frontend tests (engine.js), live REST and GraphQL, cache headers, and the seeded dataset.

All figures were measured against the running build: byte counts are wire sizes, SQL counts come from the server’s own meta counters, seed counts from the status endpoint.
